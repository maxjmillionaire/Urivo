# Specification 8 — Urivo Copilot (the conversational co-pilot)

Status: **DEFERRED — post-launch flagship.** Do not implement before Phase 2
(Stripe) and public launch. This spec queues the work so it's ready to execute.

Name: **Urivo Copilot** (not "JARVIS" — that is Marvel's trademark).

## 1. Vision

Promote today's "Ask Urivo" from a **store editor** into a **business co-pilot**:
one calm conversation that can answer questions about the founder's business and
*act* across the whole operating system — research, generation, imagery, ads,
SEO, orders, store settings — always with the founder's approval. An AI-native
commerce OS deserves an assistant that can run the business by conversation. Done
right, it is a headline feature that markets itself (spec: product is marketing).

It must feel inevitable and calm, never gimmicky. If any part reads as "AI slop"
or theatrical, it does not ship.

## 2. What already exists (the foundation)

- `lib/ai/assistant.ts` — grounded, store-aware streaming replies (`/api/ask`).
- `lib/ai/store-editor.ts` + `lib/storefront/apply-edit.ts` — propose → confirm →
  apply an edit to the real store, server re-validated (`/api/stores/[id]/edit`,
  `/edit/apply`). This is the safety model the Copilot generalizes.
- `ask-urivo.tsx` (desktop rail) + `mobile-rail.tsx` (mobile sheet) — the surface.

The Copilot keeps this surface and adds a **tool-use layer** beneath it.

## 3. Architecture — the tool layer

Use Claude tool calling (Anthropic SDK) with a typed toolbox. Each tool is a thin
wrapper over an EXISTING, already-secured server capability — the Copilot gains no
new privileges; it can only do what the founder can already do in the UI, and
every call re-runs that capability's auth → ownership → validation pipeline.

Tool categories:
- **Read (safe, auto-run):** `getStores`, `getProducts`, `getStoreOrders`,
  `getCreditBalance`, `getSeoAudit` — factual answers about the business.
- **Generative (propose a result, no side effects until confirmed):**
  `researchMarket`, `generateAdPlan`, `draftProductCopy`, `regenerateProductImage`.
- **Write (ALWAYS propose → confirm → apply):** `applyStoreEdit`,
  `addProduct`, `updateProduct`, `setStoreLive`, `updateLogo`.

The model plans; the Copilot executes read tools directly and stages write tools
as an approval card (reusing the existing EditCard pattern). Nothing that changes
data or spends credits ever runs without an explicit tap.

## 4. Safety model (non-negotiable)

- Read vs write is enforced server-side, not by the prompt.
- Every write is confirmed by the founder before execution (propose → confirm →
  apply), exactly like store edits today.
- Credit-spending actions (generation, imagery) show the cost and require confirm.
- Destructive actions (delete product, take store offline) require explicit
  confirmation and are never chained/auto-executed.
- All tool calls run through the owning API's existing RLS + ownership checks.
- Rate-limited per user; every action written to `audit_logs`.

## 5. Honesty constraints (spec: no fakeness)

- The Copilot answers only from real data. It never invents metrics.
- Business-performance answers (orders, revenue, conversion) require real Stripe
  + traffic data — so those tools return real numbers or an honest "no data yet,"
  never fabricated figures. This is why the Copilot follows launch, not precedes it.
- Design-fitness/heuristic outputs are labelled as such, never as measured results.

## 6. Voice (optional, honest)

Only if it genuinely works. Real speech-to-text (Web Speech API or a speech
provider) for input and optional TTS for replies — with a visible, truthful
listening state. No fake waveforms or "listening" theater (the old cinema's
non-functional hold-Q voice was removed for exactly this reason). Ships only when
transcription is real and reliable; otherwise omitted.

## 7. Proactive insights (later phase)

Once real order/traffic data exists, the Copilot may surface calm, opt-in nudges
("your Midnight Serum outsells everything 3:1 — want ads focused on it?"). Always
dismissible, never intrusive, never fabricated.

## 8. Prerequisites

1. Public launch complete; Stripe (Phase 2) live so business-data tools are real.
2. `ANTHROPIC_API_KEY` (already used) — Copilot uses tool-calling on the same model.
3. No new external accounts required for the core; voice may add a speech provider.

## 9. Out of scope for v1

Multi-step autonomous execution without approval; cross-account/admin actions;
scheduled/agentic background runs; any action the founder cannot already perform
in the UI.

## 10. Rollout

1. **Copilot v1 — read + generative tools:** ask about the business, run research/
   ads/copy on command (results staged, not auto-applied). Highest value, lowest risk.
2. **Copilot v2 — write tools:** full propose → confirm → apply across store,
   products, logo, live state.
3. **Copilot v3 — voice + proactive insights.**

Each phase must feel finished on its own before the next begins.
