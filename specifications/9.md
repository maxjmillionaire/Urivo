# Specification 9 — Product Merchandising (winning-store depth)

Status: **DEFERRED — build after Phase 2 (Stripe) and launch.** This is the layer
that turns a beautiful generated store into a *converting* DTC store. It builds
directly on the storefront commerce from the commerce spec (cart → Stripe Connect
checkout → orders) and cannot ship before it.

## 1. Goal

Match the merchandising depth of the best DTC product pages (Seed, etc.): variant
options, subscribe-and-save, bundles, image galleries, real reviews and honest
trust modules — all generated by Claude and rendered inside each store's own
unique design system. The AI already writes this content effortlessly; this spec
adds the data model + renderer that supports it.

Every addition holds the Max Standard: premium, calm, and — non-negotiably —
honest. No fabricated reviews, no fake urgency, no unsubstantiated claims.

## 2. What exists today (baseline)

- One price + one image + one description per product (`products` table).
- Generative storefront with a real PDP (`/store/[subdomain]/product/[id]`), cart
  and Stripe Connect checkout (one-time payment).
- The store generator (`lib/ai/store-generator.ts`, `claude-opus-4-8`) emits the
  design system + product catalogue.

This spec extends the schema, the generator's output, the renderer/PDP, and the
cart/checkout to carry the new merchandising primitives.

## 3. Features

### 3.1 Product variants (options)
- New `product_variants` table: `product_id`, `options jsonb` (e.g. `{flavor:"Mint"}`),
  `price_eur`, `sku`, `inventory_count`, `image_url`, `position`. A product declares
  its option axes (e.g. Flavor: Original/Mint/Citrus) in `products.option_schema`.
- PDP renders option selectors; the selected variant drives price, image and stock.
- Cart item references `variantId` (not just productId). Checkout re-validates the
  variant's real price/stock server-side. `order_items` snapshot the variant.

### 3.2 Subscribe & Save (merchant subscriptions)
- Per product: an optional subscription offer (interval: weekly/monthly, discount %).
- Uses **Stripe subscriptions on the merchant's connected account** (recurring price
  created on that account), so the merchant owns the recurring revenue.
- New `customer_subscriptions` record; webhook handles `invoice.paid` /
  `customer.subscription.*`. Checkout mode switches to `subscription` when chosen.
- PDP shows one-time vs subscribe cards with the honest saving (computed, not faked).

### 3.3 Bundles / tiered supply
- Quantity-break pricing (buy 3 / 6, save a computed %) and/or curated multi-product
  bundles. Modelled as `bundle_offers` (product or set → tiers with real prices).
- The "Best value" / "Most popular" badge is assigned by real math (actual lowest
  unit price / most-chosen tier), never arbitrarily.

### 3.4 Image galleries
- `products.image_url` → `products.images jsonb` (ordered array). Higgsfield generates
  multiple angles/contexts; the PDP renders a gallery with thumbnails; variants can
  map to specific images.

### 3.5 Reviews & ratings — REAL ONLY
- New `reviews` table: `product_id`, `rating` (1–5), `author`, `body`,
  `verified_purchase`, `status`, `created_at`. Aggregate rating shown on cards/PDP.
- Sources: (a) post-purchase review request emailed to real buyers (verified), or
  (b) merchant import with an explicit attestation that they are genuine.
- **The AI never writes reviews.** Until real reviews exist, the UI honestly shows
  "Be the first to review" — never a fabricated star count. (Founder ethos: fake
  reviews destroy reputation and are legally dangerous.)

### 3.6 Trust & merchandising modules
- Structured, editable modules: benefit-icon row, guarantee badges (e.g. money-back,
  secure checkout, ships-fast), certification/claim chips. Generated as *editable
  suggestions* the merchant confirms.
- Banned: fake countdowns, "only N left" scarcity that isn't real, invented awards.

## 4. AI generation

Extend the generator's schema so Claude emits (all editable, all optional):
variant option axes + values, a sensible subscribe-and-save offer, bundle tiers,
gallery prompt set, and honest trust modules. The model is fully capable of this
today — this is a schema + renderer expansion, not an AI limitation.

## 5. Honesty & legal constraints (highest authority here)

- **Reviews:** real and verified only; never AI-generated; never displayed as a
  count until genuine reviews exist.
- **Health / medical / efficacy claims:** a claims-safety pass keeps generated copy
  in defensible, non-medical language; anything reading as a clinical/health claim
  is flagged for merchant review before publish. Urivo asserts no efficacy.
- **No dark patterns:** no fake urgency, fake scarcity, or misleading "Most Popular"
  labels. Badges must be true by construction.
- The merchant is responsible for published content (AGB §6); Urivo surfaces
  suggestions and confirmations, never auto-publishes unverifiable claims.

## 6. Data model summary (new migrations)

`product_variants`, `customer_subscriptions`, `bundle_offers`, `reviews`; extend
`products` with `option_schema` + `images`; extend cart/`order_items` to carry
variant + offer references. All with RLS mirroring `products` (owner-write, public
read where the store is active); order/subscription writes are service-role only.

## 7. Pipeline discipline (spec 6.1/6.3)

Every new endpoint: authenticate → ownership → rate-limit → Zod validate → persist,
with prices/stock always recomputed server-side. Subscriptions and orders remain
webhook-authoritative and idempotent.

## 8. Rollout

1. **Galleries + variants** — the biggest lift in perceived quality; one-time checkout.
2. **Bundles / tiered pricing** — higher AOV, no new billing primitives.
3. **Subscribe & Save** — recurring revenue (needs Stripe subscriptions on Connect).
4. **Reviews** — post-purchase request flow + display.
5. **Trust modules polish.**

Each phase must feel finished before the next. The goal is not more features — it
is a generated store that looks and converts like the best stores on the internet.
