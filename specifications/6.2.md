# URIVO.AI PRODUCTION ENGINEERING BLUEPRINT — PART 6.2
# SUBJECT: BILLING, STRIPE, FINANCIAL INTEGRITY & DATA CONSISTENCY

---

## MISSION

All billing operations must be deterministic, idempotent and fully auditable.

The platform must never:

- charge twice
- lose payment events
- create duplicate subscriptions
- deduct credits incorrectly
- leave inconsistent financial records

Financial integrity takes precedence over feature velocity.

---

# SECTION 11 — STRIPE IDEMPOTENCY

Every outbound Stripe API request must use an idempotency key.

Examples:

- Checkout Session creation
- Refund creation
- Subscription updates
- Customer creation
- Invoice retries

If a request is retried because of a timeout or network failure,
the same operation must not execute twice.

---

# SECTION 12 — WEBHOOK PROCESSING

Treat Stripe webhooks as the single source of truth.

Rules:

- Verify webhook signatures.
- Reject invalid signatures.
- Process each event exactly once.
- Persist processed event IDs.
- Ignore duplicate deliveries.

Maintain a `stripe_webhook_events` table containing:

- event_id (unique)
- event_type
- received_at
- processed_at
- processing_status
- error_message (nullable)

---

# SECTION 13 — SUBSCRIPTION LIFECYCLE

Support the complete lifecycle:

- trial started
- subscription created
- upgrade
- downgrade
- renewal
- payment failed
- payment recovered
- cancellation scheduled
- cancellation completed
- refund

Application state must always reflect Stripe's authoritative status.

---

# SECTION 14 — CREDIT LEDGER

Credits must never be stored as a mutable balance only.

Implement a ledger model:

credit_transactions

Fields:

- id
- user_id
- delta
- reason
- source
- created_at

Examples:

+500 Monthly Plan
-10 Store Generation
-2 AI Rewrite
+100 Referral Bonus

Current balance is derived from transactions or maintained with
atomic updates.

---

# SECTION 15 — BILLING AUDITABILITY

Every financial event must create an immutable audit record.

Examples:

- checkout_started
- checkout_completed
- invoice_paid
- invoice_failed
- refund_issued
- affiliate_commission_paid
- credit_adjustment

Each record should include:

- user_id
- stripe_customer_id
- stripe_object_id
- timestamp
- amount
- currency
- status

---

# SECTION 16 — CURRENCY HANDLING

The client may only send:

- productId
- preferredCurrency

The server must:

1. Load the product price in EUR.
2. Apply the configured exchange rate.
3. Convert to the smallest currency unit.
4. Create the Stripe Checkout Session.

Never trust client-supplied prices.

---

# SECTION 17 — REFUNDS

Refunds must:

- be initiated only by authorized users or admins
- create an audit log
- update the billing history
- notify the customer
- avoid duplicate execution

---

# SECTION 18 — AFFILIATE COMMISSIONS

Commission payouts must occur only after successful payment.

Rules:

- no payout for failed invoices
- no payout for refunded invoices
- idempotent transfer creation
- record transfer ID
- reconcile payout status

---

# SECTION 19 — DATABASE CONSISTENCY

Operations that affect multiple tables must execute atomically.

Examples:

Store generation:

1. deduct credits
2. create store
3. create products
4. create audit log

If any step fails:

- rollback all previous steps

No partial state is permitted.

---

# SECTION 20 — BILLING OBSERVABILITY

Expose internal metrics:

- successful checkouts
- failed checkouts
- webhook latency
- webhook failures
- refunds
- active subscriptions
- monthly recurring revenue
- annual recurring revenue
- churn
- average revenue per user

Metrics should feed the analytics dashboard and monitoring system.
